# 房间同步 v2 设计与实现

状态：本次实现采用此设计，协议版本统一为 **2**。此前本地实验版本未发布，直接替换，不提供实验版本兼容层。

本方案保留当前图层、标注和文件内容的数据模型，重新设计确认、恢复、冲突处理及元数据生命周期。浏览器和 agent 使用同一套协议与校验规则。旧协议直接拒绝，要求刷新或升级，不提供兼容写入。

## 1. 设计选择与依据

采用**服务器权威状态 + 客户端乐观修改 + 连续提交序号**。一个房间的 Durable Object 负责确定提交顺序和执行数据库事务。

客户端始终区分两种数据：

```text
可见状态 = 已确认的服务器状态 + 按顺序应用的本地待确认修改
```

同步服务器状态不会产生新的本地修改。服务器确认只移除已经处理的修改，其后的本地编辑继续保留。

这沿用成熟协作系统中的几个原则：

- Replicache 将本地修改持久化、按客户端序号推送；收到服务器状态后，移除已处理修改并重新应用剩余修改。最高已处理序号与业务修改在同一事务提交。[同步模型](https://doc.replicache.dev/concepts/how-it-works)、[提交协议](https://doc.replicache.dev/reference/server-push)
- Figma 的结构化对象同步按属性处理修改，使不同对象、不同属性上的编辑能够并存；服务器定义顺序。[技术说明](https://www.figma.com/blog/how-figmas-multiplayer-technology-works/)
- Yjs 等 CRDT 适合需要自动合并细粒度文本或序列编辑的场景。本项目暂不要求多人同时编辑同一段文字或同一条路径的内部节点，因此当前实现不引入通用 CRDT/OT。[Yjs](https://github.com/yjs/yjs)

下面的具体协议、冲突策略和容量参数是本项目的设计选择，不是上述产品协议的复制，也不声称所有协作系统都应如此实现。

## 2. 保证与边界

必须保证：

1. 不同图层、不同标注上的有效修改可以并存。
2. 不会把缓存中缺失于服务器的对象自动重新创建。
3. 修改、删除和创建具有不同语义；修改不存在的对象必定失败。
4. 同一有效客户端流中的提交有序，重复投递不会重复修改业务数据。
5. 业务修改、提交进度和简短结果原子保存；成功持久化后才向客户端发布。
6. 并发冲突有明确结果，相关本地草稿不被静默丢弃。
7. 恢复失败可以退回完整快照；不能把旧修改改个版本号就视为已经解决冲突。
8. 协议存储量不随房间的终身操作次数增长。

不保证：

- 永久查询任意历史请求的完整返回值。
- 永久接受已经回收的客户端流继续提交旧队列。
- 同一文本、同一路线几何的任意并发编辑都能自动合并。
- 在数据库丢失或从旧备份恢复后，仍继续使用旧客户端流。

有限恢复窗口与数据丢失是不同的概念：客户端流过期时，本地草稿仍然保留；失效的是自动续传旧提交的资格。

## 3. 服务器保存什么

沿用 `layers`、`annotation_features`、`file_contents`。同步只增加当前状态所需的少量元数据。

| 数据         | 内容                                                                                                      | 生命周期与大小                   |
| ------------ | --------------------------------------------------------------------------------------------------------- | -------------------------------- |
| 房间同步状态 | `epoch`、`commitVersion`                                                                                  | 每房间一行                       |
| 实体版本     | 整体版本、可独立修改的字段组版本                                                                          | 每个存活实体固定数量的字段       |
| 客户端流     | 所属身份、服务器签发的 `clientId`、`lastProcessedSeq`、最近请求摘要、最近简短结果、过期时间、当前连接代次 | 每个未过期客户端一行             |
| 已删除实体   | 首版不保存永久删除表                                                                                      | 依靠完整快照恢复及严格的创建规则 |
| 历史操作     | 不保存完整请求、完整返回值或永久操作 ID 集合                                                              | 无                               |
| 增量恢复日志 | 首版不实现                                                                                                | 无                               |

`lastProcessedSeq` 表示“已经处理”，包括业务拒绝，不等于“全部成功”。最近结果必须记录成功或拒绝，不能仅凭一个序号让客户端误认为冲突已经成功保存。

最近结果仅包含：

```text
seq、accepted/rejected、commitVersion、错误码和目标、创建对象的 ID 映射、涉及字段组的版本
```

不包含几何、备注正文、完整实体、全量列表或文件字节。字段组版本只是少量名称和整数，用于确认后续草稿真正依据的版本；不存字段值历史。最近请求仅保留固定长度摘要，用于发现同一序号被错误地用于不同提交。

若有效客户端数为 C、最近结果的大小上限为 B，同步流元数据为 O(C × B)，不随历史提交总数增长。实体数据和文件本身的增长是业务容量，独立于去重成本。

## 4. 两个序号，各有一个用途

- `commitVersion`：房间共享数据的版本，供下行更新排序和检测缺口使用。一次改变共享状态的批次增加一次；被拒绝或没有实际改变的批次不增加。
- `seq`：一个客户端流内的连续提交批次序号，用于提交顺序和重复投递处理。每个终态批次都消耗一个序号。

两者不能混用。不同客户端可以同时提交各自的 `seq=5`，但服务器为实际共享状态变化安排唯一的房间顺序。

`epoch` 标识房间状态的一个世代。房间过期重建、从旧备份恢复、破坏性的协议迁移必须更换 epoch；普通进程重启或 Durable Object 休眠唤醒不更换。

## 5. 客户端流与持久化

`clientId` 由服务器显式签发，并绑定房间、epoch 和登录用户或访客身份。`submit` 不能隐式创建客户端记录。已回收、未知或不属于当前身份的客户端流拒绝续传。

每个客户端流最多有**一个已发送但尚未确认的批次**。后续编辑仍立即显示并存入本地草稿队列，不阻塞交互。

浏览器使用 IndexedDB 保存：

- 最近的已确认状态及其版本；
- 不可变的在途批次及其序号；
- 尚未冻结、允许合并的编辑意图；
- 冲突草稿、所依据的字段值和版本；
- 尚未上传的文件 Blob。

发送前先提交本地事务。收到确认后，先在本地事务中移除在途批次、应用结果和 ID 映射，再允许发送下一序号。因此一个正常恢复的客户端最多只需要服务器的最近结果。

不同标签页可以使用不同的客户端流。恢复已有本地队列时，必须对该队列取得独占写权限，使用 Web Locks；不能让两个标签页并行发送同一个流。IndexedDB 按身份和房间隔离，并能发现上次标签页留下的草稿，不能仅依赖已经消失的 sessionStorage 键找到它。有草稿的已关闭标签页优先被发现；不支持 Web Locks 的环境只建立独立日志，不自动接管旧日志，以避免并发写入。

同一客户端流重新连接时，服务器更新连接代次，使旧连接失去写入资格。多条连接争用同一流时拒绝旧连接，不让其成为两个独立的写入者。agent 的连续调用也不能并行共享同一个流；并行 agent 使用独立流。

CLI/SDK 与浏览器共用 `packages/atlas-realm-cli/src/sync-client.ts` 和 `sync-protocol.ts`。CLI 按主机、房间、客户端名和认证配置保存原子文件日志，并使用进程锁避免同一个 `--client-id` 被并行使用。`ATLAS_REALM_STATE_DIR` 可以指定日志目录。单次命令必须等待对应批次的结果，不能匹配历史事件或其他 agent 的广播作为成功。跨进程恢复时先处理日志中的在途批次和草稿。如果本次调用恢复了先前未确认的操作，CLI 返回恢复结果并标明 `requestedCommandExecuted: false`，不会同时把本次参数作为另一次新创建执行；调用者检查恢复结果后再发起新命令。SDK 可注入日志适配器；没有恢复材料时只报告“结果未知”。

## 6. 上行提交与确认

示意提交：

```json
{
  "type": "sync:submit",
  "protocol": 2,
  "epoch": "room-epoch",
  "clientId": "server-issued-client",
  "seq": 18,
  "commands": [
    {
      "type": "layer:patch",
      "layerId": "layer-a",
      "fields": {
        "name": { "expectedVersion": 42, "value": "Day one" }
      }
    }
  ]
}
```

批次冻结后，序号、命令及摘要不再改变。只有尚未发送的编辑意图可以合并或重建。

服务器先检查协议、身份、流的有效期、连接代次及大小限制，然后在 SQLite 事务内处理：

| 输入                                | 处理                                                   |
| ----------------------------------- | ------------------------------------------------------ |
| `seq = lastProcessedSeq + 1`        | 验证全部命令，原子应用或原子拒绝；更新流进度和最近结果 |
| `seq = lastProcessedSeq` 且摘要相同 | 返回最近简短结果，不修改数据、不再次广播               |
| `seq = lastProcessedSeq` 但摘要不同 | 拒绝，报告客户端流被并发使用或请求被篡改               |
| `seq < lastProcessedSeq`            | 返回已处理进度；不执行，也不伪造历史成功结果           |
| `seq > lastProcessedSeq + 1`        | 报告序号缺口，要求恢复；不执行                         |
| 流未知、过期或 epoch 不符           | 拒绝续传；不得把序号重置为 1 后自动接受                |

一个批次全成或全败。若某个命令冲突，批次内没有部分业务修改。客户端保留冲突项，将不依赖冲突项的其他意图重新验证、组成下一批次；不能把整批无限原样重试。

暂时性故障，例如数据库事务失败或文件内容尚未准备好，不消耗序号。终态业务拒绝消耗序号并记录简短结果。格式错误或不属于当前身份的流，不进入提交状态机。

正常成功后：

- 发送者收到简短确认，以及本次规范化增量；
- 其他观察者收到相同版本的增量；
- 持久化的最近结果不保存这个增量正文。

重复提交只返回简短结果。如果客户端缺少对应的共享状态，它通过完整快照补齐，服务器无需保留原始增量来复现响应。

## 7. 下行与断线恢复

首版选择**在线推送增量，重连读取完整快照**。这一选择针对当前以房间为单位的地图数据，减少实现和回收复杂度；不是认为所有规模下全量快照都更便宜。

快照包含同一个数据库观察点上的：

```text
epoch、commitVersion、layers、features、该客户端的 lastProcessedSeq 和最近简短结果
```

快照使用一致的数据库读事务，或不跨越 `await` 的同步 SQL 读取生成，不能分几次异步读取后拼接不同版本的数据。快照中不包含历史操作和文件字节。文件通过内容哈希单独读取。

恢复步骤：

1. 暂停发送，保留原有本地基线、在途批次和草稿。
2. 恢复已有流，读取原子快照和提交进度。
3. 在途序号等于服务器最高已处理序号时，使用最近结果确认成功或保留拒绝草稿。
4. 在途序号是服务器序号加一时，它尚未处理；保留原批次，恢复后按同一序号重发。
5. 本地在途序号小于服务器最高已处理序号时，视为本地队列回滚或流被错误共享；进入恢复提示，不能猜测结果或自动重放。
6. 替换已确认状态，重新应用剩余草稿，并一次性更新界面。

在线增量只按连续 `commitVersion` 应用。收到重复版本忽略；检测到缺口或 epoch 改变时，暂停应用并请求快照。同一个恢复周期只允许一个快照请求在途，合并重复触发；网络失败使用指数退避和随机抖动。普通业务冲突优先附带相关字段的当前值，或按需读取相关实体，不要求每次冲突都拉整个房间。字段正文不写入最近简短结果；重试需要查看冲突详情时读取的是当前状态，不承诺重现当时的完整错误正文。

若以后测得完整快照成为主要开销，再增加有字节数、条数和时间上限的增量窗口，同时维护 `minAvailableVersion`。早于这个位置的客户端退回快照。没有这项需求之前，不建立永久变更日志。

## 8. 并发修改的业务规则

冲突检测的默认单位是**字段组**。

| 数据                     | 独立合并单位与规则                                           |
| ------------------------ | ------------------------------------------------------------ |
| 图层名称、可见性         | 各自独立的字段版本                                           |
| 图层样式                 | 颜色、宽度、透明度等独立字段                                 |
| 标注标签、备注、样式     | 独立字段；同一正文的并发编辑提示冲突                         |
| 点坐标、路径或多边形几何 | 每个标注的几何为一个原子字段组                               |
| 规划路线                 | waypoints、geometry、profile 及关联距离/时长作为一个一致性组 |
| 标注所属图层             | 独立的 membership 字段组，同时校验目标父层存在且类型正确     |
| 文件替换                 | 内容哈希及其类型、编码、长度、边界等关联元数据作为一个原子组 |
| 顺序                     | 语义化移动命令，见下一节                                     |

字段组由服务端 schema 明确定义，拒绝任意新增字段组名。每个字段组保存最近改变它的服务器版本。提交只检查它实际修改的字段组：

- A 改名称、B 改颜色：两者均可成功。
- A、B 基于同一版本修改名称：先提交者成功；后者若目标值不同则冲突。
- 目标值已经等于服务器值：可以作为成功的无变化提交确认，不增加业务版本。
- 一个字段被别人修改后又改回原值，仍可能因版本变化发生冲突；不能靠客户端时间戳决定谁更新。

连续本地编辑需要保留因果关系。例如先把名称改为 B，尚未确认时又改为 C，第二个意图依赖第一个意图的结果。前一个批次确认后，后续意图从确认中的字段版本获得真实基线；不能预估房间的下一版本，也不能把基线替换为另一个用户随后写入的更高版本。前序批次失败时，其依赖意图进入重新验证或冲突处理；独立意图继续。

服务端校验是最终判定。客户端重放用于预测，不是绕过版本检查的授权。

冲突 UI 保存并展示：编辑时的基线、本地意图、当前服务器值。自动保留互不重叠的修改；同一字段组无法安全合并时，才让用户选择当前版本、自己的版本或编辑新版本。选择自己的版本会形成一个明确基于当前状态的新提交。

## 9. 创建、删除与“图层复活”

删除安全主要来自命令语义和确认进度，而不是永久记住所有删除操作。

- `create` 只表达真实的新建意图；服务器分配新的实体 ID。客户端缓存不能指定一个历史实体 ID 来要求重新创建。
- 未确认的新建对象使用本地临时引用。批次内可以引用前面创建的对象；服务器返回临时引用到正式 ID 的映射。后续未发送草稿在确认后转换引用。
- 有效流内重试创建批次，由连续序号去重，返回最近的 ID 映射，不创建第二份对象。
- `patch`、`move`、`replace` 只作用于存在的对象；不存在时返回 `target_missing`。不提供隐式创建的 `upsert`。
- `delete` 表示对指定实体的显式删除意图；重复删除是无变化成功。删除图层和其仍属于该图层的标注在同一事务发生。
- 本设计选择删除优先于旧编辑：编辑先提交、删除后提交，最终删除；删除先提交、编辑后提交，编辑失败。删除不因为名称或颜色刚改变就被整行版本检查阻止。
- 若标注先移到别的图层，再删除原图层，该标注保留；若原图层先删除，随后移动旧标注则失败。

客户端更新快照时，缺失对象从已确认状态中移除；针对它的本地编辑转为冲突草稿，不能触发创建。

在客户端流已过期、且某个创建批次的确认状态丢失时，客户端不能断定它“从未创建过”：对象也可能已经创建又被删除。这种草稿进入结果未知的恢复流程；用户明确选择保留为新对象时，才以新 ID 创建。不能自动把旧创建命令包装进新流提交。

由于首版不提供历史增量补拉，并且上述创建和续传规则阻止旧 ID 复用，服务器不需要永久 tombstone 表。若未来引入增量窗口，删除事件必须进入同一有限窗口，窗口之外强制快照。

现有对象的 ID 保留不变。CLI 使用 `add` 创建新对象、`update` 修改已有对象、`layers replace --id <id>` 替换文件内容；移除含糊的 `upsert` 操作，已有目标不会由 `add` 隐式改写，缺失目标也不会由 `update` 隐式创建。CLI 的已有 ID 用于定位对象；新建命令通过本地引用关联批量输入，并从结果中获得正式 ID。业务需要的可读名称或外部标识应与实体 ID 分开。

## 10. 排序

上行发送 `moveBefore(itemId, anchorId|null, expectedPositionVersion)`，不上传客户端的完整顺序数组或一批从旧列表计算的 sortKey。`null` 表示移到末尾。

- 服务器在当前列表中解释锚点，并原子计算新的顺序。
- 不同对象的移动按服务器顺序处理；同一对象基于旧位置版本再次移动时提示冲突。
- 对象或非空锚点已删除时拒绝，不猜测用户要移到哪里。
- 新建对象可以使用同批次内的临时引用作为锚点。
- `sortKey` 是服务器维护的排序表示。首版可以沿用现有字符串排序字段；如需重新分配多个排序键，事务完成并广播实际变化的键。
- 仅因排序键重新编号而位置不变的对象，不增加其语义位置版本。不能因为内部编号整理制造用户冲突。

后续可采用分数排序键减少重写范围，但这不是同步正确性的前提。

## 11. 文件与高频交互

文件字节保持内容寻址，与实体元数据分开。上传和哈希校验完成后，才能提交创建或替换命令；创建图层的确认本身不重新传输文件字节。

未引用内容可按独立容量和时间策略清理。若它在提交前已被清理，返回暂时性的 `content_needed`，客户端先补传，再重试同一批次。该结果不消耗提交序号。

异步下载、解压和渲染必须绑定当前房间世代、实体 ID 和内容哈希；完成后再次检查当前已确认状态或有效本地草稿是否仍引用该内容。删除或替换后完成的旧异步任务不得把旧对象加回地图。

节省消息的主要手段是减少无意义的中间编辑：

- 尚未发送的同字段连续设值可以合并，例如名称输入、颜色和透明度滑动。合并保留最早的基线和依赖，使用最后的目标值，不能同时刷新基线来掩盖并发修改。
- 拖动预览和光标属于临时协作状态，使用节流的 presence 消息；明确的编辑提交边界才写业务数据。
- agent 可批量提交多个独立对象，受同样的事务和大小限制。
- 已发送批次不能为了合并而修改内容；后续编辑进入下一批。

## 12. 元数据回收与离线支持

客户端流使用服务器时间管理的可续期租约。成功恢复、有效提交或受限频率的活动更新可以延长租约；不为每次光标移动写数据库。

过期流先失去提交资格，再回收它的进度和最近结果。过期判断在每次恢复和提交时执行，不能只依赖定时清理任务是否及时运行。旧流无法通过普通 `submit` 自行重新注册。

恢复结果分三类：

| 情况                                     | 行为                                                                   |
| ---------------------------------------- | ---------------------------------------------------------------------- |
| 流有效，仅断线或版本落后                 | 自动获取最新状态、确认在途提交并重新应用草稿                           |
| 流有效，但修改发生业务冲突               | 保留冲突草稿；不要求其他无冲突编辑人工发布                             |
| 流已过期、epoch 改变或本地队列状态不可信 | 建立新流、读取最新状态；将旧意图送入恢复流程，绝不自动重发冻结的旧批次 |

离线时长只决定是否还能自动续传旧流，不是所有冲突的判断依据。有效期内也可能冲突；超出有效期的未发送草稿也可能经比较后安全恢复。无法判断是否已提交的在途意图需要明确提示，尤其是创建。

当前容量参数如下；它们是实现起点，后续可按观测结果调整：

| 参数                 | 建议起点 | 作用                               |
| -------------------- | -------- | ---------------------------------- |
| 客户端流闲置有效期   | 7 天     | 限定服务器自动续传承诺             |
| 每流在途批次         | 1        | 使最近一条简短结果足以恢复正常队列 |
| 每批命令上限         | 64       | 限制事务执行时间和结果 ID 映射大小 |
| 普通批次编码大小上限 | 256 KiB  | 限制解析和事务输入开销             |
| 最近简短结果上限     | 16 KiB   | 明确每客户端元数据的容量上界       |

超过普通批次上限的单个几何修改应走内容寻址的上传准备步骤，再由命令引用已验证内容；不能拆成会破坏几何一致性的多个半成品修改。结果大小在执行前按命令数量、ID 长度和错误格式验证，不能提交后才发现结果无法保存。

应限制每身份、每房间的流创建速率与未过期流数量，并定期清理过期行。否则即便每行很小，任意创建客户端 ID 仍会导致无界增长。当前上限为每房间 1024 个流、每身份每房间 128 个流，以及每身份每房间每分钟最多创建 16 个流。达到上限时明确拒绝新流；过期行在创建新流和房间维护时清理。

## 13. 开销与可观测性

有 N 个在线客户端（包含发送者）时，一次改变共享状态的批次通常是一个上行批次、一个发送者确认及 N−1 份广播。没有全员互相确认。与逐操作协议相比，合并和批量提交可以减少消息；字段增量和排序移动也减少正文大小。

数据库额外成本主要是一次客户端进度更新、必要的字段版本检查和房间版本更新，与业务修改合并在同一事务。重复投递只读取当前进度和简短结果。完整快照在连接、缺口或必要恢复时读取，不在每个成功操作后发送。

必须观察而非凭测试通过推断性能：

- 每秒命令数、批次数、入站/出站字节；
- 批次事务时长和确认延迟；
- 快照大小、生成频率和触发原因；
- 不同原因的冲突率、重复率、恢复失败率；
- 客户端流行数、总字节数、过期清理延迟；
- 本地待发送草稿数量和存储失败。

管理员可以发送 `{"type":"sync:stats:request","protocol":2}` 获取当前实例的提交数、命令数、输入字节、快照次数/字节、处理耗时、结果分类，以及数据库中的客户端行数和逻辑字节数。计数在实例重启后归零，不建立永久指标历史；逻辑字节不等于 SQLite 实际磁盘占用或网络计费字节。完整出口流量应结合运行平台指标观察。

是否增加增量恢复、调整批量大小或细化某种数据的协作算法，应由这些指标决定。

## 14. 实现结构与数据升级

| 模块                                            | 职责                                                |
| ----------------------------------------------- | --------------------------------------------------- |
| `packages/atlas-realm-cli/src/sync-protocol.ts` | 共享命令、字段组、版本和排序定义                    |
| `packages/atlas-realm-cli/src/sync-client.ts`   | 浏览器与 CLI 共用的草稿、批次确认、合并与恢复状态机 |
| `src/worker/room-sync.ts`                       | 流注册、租约、连接代次校验、连续序号和简短结果      |
| `src/worker/room-sync-commands.ts`              | 字段校验、服务器 ID 分配、语义移动和批次执行        |
| `src/worker/room-storage.ts`                    | 当前实体字段版本和有界客户端表                      |
| `src/sync-journal.ts`                           | IndexedDB 日志与标签页写锁                          |
| `packages/atlas-realm-cli/src/sync-journal.ts`  | CLI 原子文件日志与进程写锁                          |

命令执行器先在暂存状态上验证完整批次，业务校验全部通过后才写业务行。外层 SQLite 事务将业务行、房间版本、客户端进度和最近结果一并提交。业务拒绝只更新进度和简短拒绝结果，不留下部分业务写入。

已有 `layers` 和 `annotation_features` 表增加 `field_versions_json` 列；已有实体从字段版本 0 开始，不改写其业务内容或 ID。新增 `sync_clients` 表，不创建永久操作回执、历史操作 ID 或永久删除表。实验实现的旧协议代码直接移除，无兼容读取/写入分支。

WebSocket 必须声明 `syncProtocol=2`；旧协议连接或旧写入消息直接拒绝并断开。浏览器、CLI 与服务端一起升级；现有房间数据保留。未发布实验版本的数据和队列不属于兼容范围。

## 15. 验收场景

以下是实现的回归验收清单；实际执行结果以单元、Worker 和浏览器测试输出为准：

- 同一有效批次重复投递只改变业务数据一次；最近请求摘要不匹配时拒绝。
- 在提交事务前、提交后发送确认前、客户端持久化确认前分别崩溃，恢复结果仍一致。
- 被拒绝批次的确认丢失后，仍恢复为拒绝而不是成功；独立草稿可以继续。
- 同字段冲突、不同字段合并、不同标注并行编辑符合既定规则；连续本地编辑在前序确认或拒绝后仍使用正确的字段基线。
- 删除与改名、几何编辑、标注跨图层移动的不同到达顺序均不造成复活或孤儿。
- 创建确认丢失后再次连接不重复创建；过期流的未知创建结果不自动转为新创建。
- 一个批次失败不留下部分实体、错误序号或已发布的半成品消息。
- 快照包含一致的图层、标注和客户端进度；消息重复、缺口及延迟能够恢复。
- 两个标签页争用同一流时有明确拒绝或接管结果；关闭标签页后的草稿可被发现。
- 客户端流过期前后、数据库恢复换 epoch、权限变更均遵守续传边界。
- 图层排序与并发创建/删除/移动不会恢复旧顺序数组，也不会产生无效锚点引用。
- 文件上传确认丢失、未引用内容被清理、删除后的解压完成均可安全处理。
- 固定有效客户端数下执行大量操作后，同步元数据大小趋于稳定；增长不能与终身操作数成正比。
- 所有协议入口拒绝旧客户端，不存在绕过 v2 校验的旧列表或旧写入分支。
