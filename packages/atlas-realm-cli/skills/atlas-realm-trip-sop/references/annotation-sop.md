# Atlas Realm 房间标注 SOP（通用标准 v1.2）

> 提炼自实际路书房间的做法，配合客户端渲染器（`src/annotation-renderer.ts`）默认值核对。
> 适用：把任意行程（自驾、徒步、离岛、巡礼、考察）沉淀成一张可协作的地图房间。

---

## 0. 一句话标准

**一层 = 一个行程单元（一天 / 一个岛 / 一类专题）；一条 route = 一段真实道路；一个 point = 一个有日期、有前后接续、有出处的位点。**
配色按“天/区域”分而不是按“类型”分；label 短、emoji 开头；细节全部进 note（Markdown）。

---

## 1. 数据模型（写之前先认清四件事）

- `layer` 有 `id` / `name` / `sortKey` / `visible`；annotation 图层承载手工标注，file 图层承载 GeoJSON/GPX。
- `annotation` 有 `id` / `layerId` / `featureType` / `payload` / `sortKey`。
  - `featureType`: `point` | `text` | `path` | `polygon` | `route`
- 路由几何**由调用方提供**，服务端不做寻路：`--waypoints`（起讫/途经）+ `--geometry`（真实道路点串）。
- 所有坐标一律 **WGS-84**（高德 GCJ-02 必须先转换，否则整体偏移 300–500m）。

## 2. 命名规范

| 对象     | 规范                                                                                                   | 本房间实例                                                                             |
| -------- | ------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------- |
| 图层 id  | **服务端分配** `layer-<uuid>`，不可指定；语义写进图层名                                                | `annotation-default`（默认层，老房间保留原 id）                                        |
| 图层名   | `emoji + Day N + 日期 + 起→终`（单日可省 Day）                                                         | `🚗 Day 2 8/6 小平→稚内`、`⛴️ Day 3-4 8/7-8 利尻·礼文`、`🥾 礼文岛 8/8 桃岩徒步+观光B` |
| 图层顺序 | `sortKey` 由服务端按位置维护（10/20/30…，9 位补零）；顺序用 `annotations layers reorder` 一次传全部 id | 第一层恒为 `📍 POI & 宿泊`                                                             |
| 标注 id  | **服务端分配** `feature-<uuid>`；语义放 label / note，老房间的可读 id 继续可寻址                       | `seg-d1-01`、`ferry-d3-rishiri`（同步 v2 之前创建的对象）                              |
| label    | `emoji + 名称(+日期/时间)`，一行，不写 detail                                                          | `🏔️ 神威岬 8/5`、`⛴️ 鴛泊FT 09:05発`                                                   |

> **id 与顺序都归服务端管**（房间同步 v2 §9–§10）：`create` 一定 mint 新 id，客户端传的 `--id` 只是批次内本地引用（不会落库），`--sort-key` 被忽略并按位置重编号。所以「用 `seg-d1-01` 这种 id 建对象」只在 v2 之前成立；新对象把语义写进 label / note，排序统一走 `annotations reorder`。

**label 命名习惯**：自驾段 `A→B 距离 时长`、徒步 `🥾 日期 起点→终点`、点位 `emoji 名称 日期`；路线分类靠 emoji / note，不靠 id 前缀。

## 3A. 线与点的样式规范（与客户端默认值一致）

**线宽（route/path）**

- `4` — 自驾主线默认
- `5` — 长干线段 / 当日重点段（如 109km 的 天文台→稚内灯台）
- `3.5` — 接驳支线（巴士短驳、港区）
- 客户端会给 `solid` 线自动加 3px 深色 casing（`#111827`），视觉宽度 ≈ 设定值 +3，别自己再加粗；`dashed/dotted` 不套 casing。
- 参数名是 `--width`，写成 `--line-width` 会被**静默忽略**（线停在默认宽度）；`route/path/polygon` 的样式参数统一为 `--width / --color / --opacity / --line-style`。

**线型**：`solid` 自驾/巴士主线 · `dashed` 渡轮（跨海 3 点直线即可）· `dotted` 备选/绕行。

**透明度**：自驾 `0.9` · 徒步 `0.85` · 渡轮 `0.8` · 观光巴士 `0.95`（强调）。

**朝向**：自驾/巴士/徒步全部 `--directed true`（箭头按 width 自动缩放）。

**点位**：圆点 radius 6、白描边 2px；`text` 型在 zoom<11 退化为小圆点、≥11 展开成卡片（需固定尺寸时显式给 `width`，本房间用 154）。

## 3B. 配色 SOP

### 3B.1 色板来源（唯二约束）

**只用 Tailwind CSS 默认调色板；深浅只在同族内跳 2 档（`-400` ↔ `-600`，或加密时 `-400` ↔ `-700`），不要用连续档。禁止自定义 hex，禁止渐变。**
本房间 12 个色值 100% 命中 Tailwind 默认板——这不是巧合，是可直接继承的标准（档位用法需按 3B.2 修正）。

```
#3b82f6 blue-500      #2563eb blue-600     #8b5cf6 violet-500   #a78bfa violet-400
#ec4899 pink-500      #f59e0b amber-500    #f97316 orange-500   #06b6d4 cyan-500
#10b981 emerald-500   #84cc16 lime-500     #ef4444 red-500      #0ea5e9 sky-500
```

### 3B.2 分配优先级：先语义 → 再单元 → 最后专题

**① 语义色：默认「不设色」，颜色通道只留给「天」**

原则是**一色一义**——颜色这一个通道只编码“阶段（天/岛）”，其他语义用 emoji + label + 线型编码。

| 语义               | 处理方式                                                                                                                  |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------- |
| 住宿 / 营地        | **继承当天单元色** + `🏨` 前缀（本房间给住宿单配 violet-400，结果与 Day2 的 violet-500 只差 ΔE13 → 被读成同一天，是反例） |
| 机场 / 港口 / 车站 | **继承当天单元色** + `✈️`/`⛴️`/`🚌` 前缀                                                                                  |
| 取车 / 还车        | 继承当天单元色 + `🚗`/`🔑` 前缀                                                                                           |
| 警示 / 事故地      | 继承当天单元色 + `⚠️`（唯一的破例色是 `#ef4444` red-500，且全房间只此一色，仅用于真正危险点）                             |

若行程确实需要一个“色带之外”的基础设施色（例如住宿要跳出地图），允许全房间指定**唯一一个**固定色，但必须与色带每一档 **ΔE ≥ 20**。

**② 单元色（天 / 岛 / 专题）：「同族成对 + 色相递进」**

这是满足「相邻天既看得出区别、又看得出是同一个系列」的核心规则：

1. **相邻两天共用同一色相**（同族）；**深度拉开 2 档**（`-400` ↔ `-600`）→ 同系列 + 一眼可辨。
2. **每跨一对，色相前进一族**（blue → violet → pink → amber，相邻族间距 ≥ 40°）→ 地图上能看出行程在推进。
3. 单日单元多、需要更强区分时，深度改跳 3 档（`-400` ↔ `-700`）。

> 为什么必须跳档：Tailwind 同族相邻档之间 ΔE 只有 **5～11**，逐档推进的相邻色相也只有 **5～12**——都低于可辨阈值，实际看不出是哪一天。

**实测（CIEDE2000）：**

| 方案                               | 相邻最小 ΔE | 结论   |
| ---------------------------------- | ----------- | ------ |
| 单色同族 · 连续档（blue-300→900）  | 5.4         | ✗ 太像 |
| 相邻色相逐档（sky→rose）           | 5.0         | ✗ 太像 |
| 相邻色相跳一档                     | 12.1        | △ 勉强 |
| **同族成对 · 深浅跳 2 档（推荐）** | **16.2**    | ✓      |
| 同族成对 · 深浅跳 3 档（加密变体） | 24.2        | ✓ 最强 |

**默认色带（8 单元，同族的两个成员相邻）：**

```
Day1 blue-400    #60a5fa     Day2 blue-600    #2563eb
Day3 violet-400  #a78bfa     Day4 violet-600  #7c3aed
Day5 pink-400    #f472b6     Day6 pink-600    #db2777
Day7 amber-400   #fbbf24     Day8 amber-600   #d97706
```

超过 8 个单元：继续沿色相（fuchsia → rose → …）或回到本族 `-300/-800` 再走一圈。族序按行程主旨选（海/冷 → blue 起步；山 → violet 起步；花田 → emerald 起步），**起点可变，规则不变**。

**③ 专题色（与日期正交的兴趣点）**

专题层也是“一个单元”，**同样占用色带里的一档**（接在最后一天之后继续走色带），不要另开色相。

| 专题             | 取色                                               |
| ---------------- | -------------------------------------------------- |
| 食品工厂见学     | 色带下一档（本房间是第 6 单元 → 接 pink-600 之后） |
| 自然 / 花田 / 湖 | 同上；自然类可以整体用同一档，不再细分             |
| 一般 POI / 城镇  | 同上，随单元走                                     |
| 天气看板等文本卡 | 同上（文本卡在图上不显眼，用当天档即可）           |

### 3B.3 继承规则（这条最关键）

**点的颜色 = 它所属单元（天/岛/专题）的路线色**；语义要素（住宿/机场/港口/取还车）同样继承，靠 emoji 区分。
本房间实测：8/5 的点全是 blue、8/6 全是 violet、8/7-8 全是 cyan、8/9 全是 pink——完全一致。
→ **不要给每个点单独挑色**，否则 100 个标注就是 100 个色，地图变成调色盘。

### 3B.4 预算与约束

- **可辨硬指标**：任意两个相邻单元的 ΔE(CIEDE2000) **≥ 15**（12–15 勉强，< 12 视为同色）。
- **同系列硬指标**：相邻单元必须同色相（或色相跨度 ≤ 45°）。
- 一个房间 **≤ 8 个单元档**；色相种类 **≤ 5 族**。
- **一色一义**：同一色相/同一档位在一个房间内只出现一次。
- 同一层内不出现两个 ΔE < 15 且不同族的色（`emerald-500` 与 `lime-500` 只差 20°，肉眼分不出）。
- 强调重要程度用 **透明度 / 线宽 / 线型**，不靠换色相（换色相会破坏“一天一色”的记忆）。

### 3B.5 本房间按新规则的重排（before → after）

| 单元               | 现状                                                           | 新规则下                                        |
| ------------------ | -------------------------------------------------------------- | ----------------------------------------------- |
| Day1 札幌→小平     | `#3b82f6` blue-500                                             | `#60a5fa` blue-400                              |
| Day2 小平→稚内     | `#8b5cf6` violet-500                                           | `#2563eb` blue-600 ← 与 Day1 同族               |
| Day3-4 离岛        | `#06b6d4` cyan（渡轮）+`#f59e0b`（巴士）+`#ec4899`（徒步）三种 | `#a78bfa` violet-400 一种（渡轮 dashed 同色相） |
| Day5 稚内→朱鞠内湖 | `#ec4899` pink-500                                             | `#7c3aed` violet-600 ← 与离岛同族               |
| Day6 朱鞠内湖→札幌 | `#f59e0b` amber-500                                            | `#f472b6` pink-400                              |
| 专题（食品工厂等） | `#f97316` orange-500                                           | `#db2777` pink-600 ← 与 Day6 同族               |
| 住宿 / 机场 / 港口 | 各自独立色（住宿 `#a78bfa` 与 Day2 撞 ΔE13）                   | 全部继承当天单元色 + 🏨/✈️/⛴️                   |

结果：相邻最小 ΔE 从「住宿 13 / 专题 16」提升到 **≥ 16**，同时每一天都能找到自己的“同族兄弟”。

### 3B.6 新房间配色模板（复制即用）

```
① 选起点族：按行程主轴（海/冷 → blue；山/高原 → violet；花田/森林 → emerald；沙漠/荒野 → amber）
② 沿色带逐对分配（同族成对、深浅跳 2 档）：
   Day1 blue-400   #60a5fa      Day2 blue-600   #2563eb
   Day3 violet-400 #a78bfa      Day4 violet-600 #7c3aed
   Day5 pink-400   #f472b6      Day6 pink-600   #db2777
   Day7 amber-400  #fbbf24      Day8 amber-600  #d97706
   （单元 > 8：继续 fuchsia-400/600 → rose-400/600，或回本族 -300/-800）
③ 专题层接在最后一档之后继续走，不另开色相
④ 语义要素（住宿/机场/港口/取还车）继承当天档 + emoji；唯一破例色 = red-500 警示
⑤ 线宽/线型/opacity 表达重要程度（见 3A），色相不动
```

校验：把相邻单元的色值跑一遍 CIEDE2000，最小 ΔE 必须 ≥ 15。

### 3B.7 配色校验清单

- [ ] 相邻单元跑一遍 CIEDE2000：最小 ΔE **≥ 15**
- [ ] 相邻单元同族（或色相跨度 ≤ 45°）——「同一个系列」
- [ ] 所有色值都能在 Tailwind 默认板里找到，且**同一档位不重复使用**
- [ ] 抽查任意点：颜色 == 其所属单元的路线色（不做单独挑色）
- [ ] 住宿/机场/港口等语义要素颜色 == 当天单元色，仅靠 emoji 区分
- [ ] 渡轮/徒步等 dashed 段用的是**同色相 + 低 opacity**，而非新色相
- [ ] 色带示意（D1-Dn 色块）附在计划文档或房间说明里，便于他人沿用

## 4. note 内容结构（Markdown，渲染在弹窗里）

**点位 note 三段式**

```
emoji **名称** — 日期/时间
📍 地点 · 特色一句话
← 上一站 24km 20m | → 下一站 35km 40m
[官网/维基/Booking 链接]
```

**路线 note**

```
🚗 8/9 **稚内→宗谷岬**
📏 31km | ⏱ 23min
途经亮点（宗谷丘陵·白い道）
出发地/到达地信息
```

**符号词典**：`📍` 位置 · `📏` 距离 · `⏱` 时长 · `⏰` 时刻 · `💰` 票价 · `🏨` 住宿 · `⛴️` 船 · `🚌` 巴士 · `🥾` 徒步 · `📈` 累计爬升 · `⚠️` 风险提醒 · `←/→` 前后接续。

**规则**

- 每个点必须带**日期**；跨天写区间（`8/6-8 宿3晚`）。
- 段间的 `← / → 距离 时间` 必须与 route 的 `distanceText/durationText` 对得上（自检手段）。
- 长链接（天气看板、共享表格）**只做一条 text 标注**；关键节点（取车/还车/住宿）可重复贴一次。
- 超 3 行的 note 用 `--note-file` 传 .md，避免 shell 转义破坏换行。
- 空 note 允许（纯分段路线），但不要把说明写进 label。

## 5. 图层组织顺序（固定骨架）

```
000010  📍 POI & 宿泊          ← 全程 POI、机场、港口、住宿、取还车、天气看板
000020  🚗 Day 1 ...
000030  🚗 Day 2 ...
...
0003x0  🚌 / 🥾 离岛专题       ← 单岛线路（观光巴士 + 徒步）
0003x0  🍫 专题层（工厂见学等） ← 与日期正交的兴趣点
```

- 一层只装一个行程单元；同一天路线按行进顺序 `000010/000020/...` 递增，id 序号与顺序一致。
- 跨天共用要素（住宿、取车点）只放 `POI & 宿泊`，不复制到每日层。
- 单岛/单日徒步这种“内部还有多条线”的单元独占一层（`rishiri-cycle` / `rebun-hike`）。

## 6. 制作流程（CLI）

非交互登录（房间开了权限控制时）：`login --start-only` 拿 `verificationUrl`/`userCode` 发给用户，授权完成后用 `--flow-id` 续跑，别把登录进程挂着等。

```bash
# 0. 只读盘点（不刷新 agent 活跃状态）
#    快照常 >1MB（几何点串占大头），务必重定向到文件再解析，别直接读终端输出（会截断）
atlas-realm --host https://map.mgt.moe --room <room> --client-id agent-planner \
  --client-type query snapshot --json > /tmp/snap.json

# 1. 建层（先建层再写点，--layer-id 指向不存在的层会崩）
#    id 由服务端分配：从返回结果取 layer-<uuid>，之后 --layer-id 用它
#    layers add --opacity 首次上传可能不生效，落好后看一眼 snapshot，需要时补 layers update <id> --opacity
atlas-realm ... annotations layers add --name "🚗 8/5 札幌→小平" --json

# 2. 外部寻路拿真实道路 → 转 WGS-84 → 写入
#    标注 id 同样由服务端分配（返回 feature-<uuid>）；--id 只是批次内本地引用
#    几何点串是平铺 [[lng,lat],…]（--feature-file 里也一样），传 GeoJSON Geometry 会退化成直连
atlas-realm ... annotations add route --layer-id <layer-uuid> \
  --waypoints "141.350787,43.068655;140.346692,43.33357" \
  --geometry "<OSRM geometry 点串>" \
  --profile driving --label "札幌→神威岬 104km 1h40m" \
  --color "#3b82f6" --width 4 --opacity 0.9 --line-style solid \
  --distance-text "106km" --duration-text "1h21m" --directed true --json

# 3. 点位 / 长文本
atlas-realm ... annotations add point --layer-id <layer-uuid> --lng 140.346692 --lat 43.33357 \
  --label "🏔️ 神威岬 8/5" --color "#3b82f6" --note-file ./kamui.md --json
atlas-realm ... annotations add text --layer-id <layer-uuid> --coordinate "142.5,44.5" \
  --label "🌤️ 天气看板 8/4-11" --note-file ./weather.md --json

# 4. 顺序（同级 id 全部按目标顺序传；局部传只把这几条挪到最前）
atlas-realm ... annotations reorder <feature-uuid-1> <feature-uuid-2> --layer-id <layer-uuid> --json

# 5. 回读验证（用返回的真实 id）
atlas-realm ... annotations get <feature-uuid> --json
```

顺序原则：**snapshot → 建层 → 写 route（带真实 geometry）→ 写 point → 回读**。一次只做一个 mutation。

## 7. 验收 Checklist

- [ ] 坐标全为 WGS-84（高德来源已转换）
- [ ] 每条 route 都有真实 `geometry`（不是 waypoints 直连），跨海段才用 3 点直线
- [ ] 每条 route 都带 `distanceText` + `durationText`，且与前后点的 `←/→` 一致
- [ ] 每个 point 的 label 有日期，note 有出处链接
- [ ] 每层都有 emoji 名称，第一层恒为 `📍 POI & 宿泊`
- [ ] 配色通过 3B.7 的六条校验
- [ ] 顺序用 `annotations layers reorder` / `annotations reorder` 显式指定过；新建对象的 id 一律从返回结果取（不假设自己传的 `--id`）
- [ ] 长文本走 `--note-file`，未在 label 里塞说明
- [ ] 完成后 `snapshot` 复查 + 目视一次（样式字段名必须用 `--width/--color/--opacity/--line-style`）
